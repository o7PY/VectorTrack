1The 60-second pitch

VectorTrack is a browser-based robotics simulator. You pick a mode (line follower or maze solver), a map, a robot and an algorithm, and watch the robot run in real time in 3D or 2D. You can tune PID gains live, build your own maps in a map editor, and write your own algorithms in a small purpose-built language (VTL) with a custom sensor layout editor.

It is entirely client-side: a static bundle on GitHub Pages, no backend, no accounts, state in localStorage. The interesting engineering is in three places: a deterministic simulation core that is independent of rendering, a safe custom language with compile-time cost guarantees, and a persistence layer that has survived three schema generations without losing user data.

3Core architecture

The single most important rule: the simulation is 2D and knows nothing about rendering.

UI layer (React): selectors, PID panel, playback, telemetry
        | reads state, dispatches commands
Simulation core (pure TS, no DOM): fixed-step loop, kinematics,
        sensor sampling, algorithm controllers
        | same RobotState feeds both renderers
2D renderer (Canvas)      3D renderer (Three.js / R3F)
  • src/sim has zero imports from React or Three.js, so it runs and is unit-tested in plain Node.
  • Both renderers read the same state, so 2D and 3D can never disagree about where the robot is.
  • Swapping or adding a renderer does not touch simulation code.
Why it matters: it is what made headless verification possible. I could run a complete lap in a unit test or script and assert on the outcome, without a browser or GPU.

4Simulation: loop, kinematics, determinism

Fixed timestep

dt = 1/120 s, decoupled from the render framerate by an accumulator. Speed multipliers (0.25x to 4x) change how many sim steps run per frame rather than changing dt, so results are identical at any speed.

Kinematics

Differential drive, no slip, no acceleration ramp:

v     = (vL + vR) / 2
omega = (vR - vL) / wheelBase
x' = x + v*cos(theta)*dt   y' = y + v*sin(theta)*dt   theta' = theta + omega*dt

Wheel speeds are clamped to ±maxWheelSpeed. Deliberately no rigid-body physics engine: a kinematic model is enough to teach control, is cheap, and is deterministic.

Determinism

Same map + robot + algorithm + params ⇒ identical trajectory. There is no randomness builtin, evaluation is strictly source-ordered, and tests assert two runs match exactly. Determinism makes bugs reproducible and lets the app compare best times fairly.

Tab visibility

The loop pauses outright when document.hidden. A background tab (or automation clock) would otherwise accumulate a huge catch-up delta; the loop clamps dt, so it would limp along instead of running correctly. Found while capturing screenshots.

5Sensors and line error

  • Line mode: N downward reflectance sensors. Each samples a small disc of a 1 px = 1 mm occupancy bitmap under its world position and averages to a float from 0 (white) to 1 (black).
  • Maze mode: distance sensors implemented as raycasts against wall segments, returning distance capped at max range.

Normalized error

The line error is Σ(xᵢ·sᵢ)/Σ(sᵢ) divided by the half-span, so it is always in [-1, 1] regardless of sensor count. That lets one algorithm and one gain scale work for 3-sensor and 5-sensor robots and for custom layouts. When every sensor reads white, the last known error is held; losing the line for more than 1.5 s fails the run.

Trade-off: normalizing changed the effective gain for the 5-sensor robot (its raw error range halved). I re-fit a single global ERROR_GAIN_SCALE (170 → 340) empirically rather than exactly, since one constant cannot reproduce both robots' old trajectories. The Scout got twice as aggressive and still clears every non-hard-corner map; the Ranger had no headroom to stay at half correction.

6Built-in algorithms and PID tuning

Line: Bang-Bang, Proportional, PID. Maze: Wall Follower, Flood Fill. All are native TypeScript behind a common controller interface; VTL equivalents ship as starter templates and are checked against the natives with equivalence tests.

  • Gains have slider plus numeric input, and changes apply live on the next tick; watching oscillation appear as you raise Kp or vanish as you raise Kd is the headline feature.
  • Integral term has clamped anti-windup. Derivative is low-pass filtered (tau 0.12 s) because at 120 Hz the raw derivative is huge and noisy.
  • Tuned gains persist per (robot, algorithm).

Gain scaling gotcha (worth knowing cold)

Error is dimensionless in [-1, 1], but wheel speeds are in mm/s. ERROR_GAIN_SCALE = 340 converts the P/I sum into a wheel-speed differential, and the D term gets its own much smaller D_GAIN_SCALE = 20 because its units carry an implicit 1/dt. Reusing the P scale for D made default Kd demand reversed wheels, which looked like the robot "struggling to move". The same scale applies inside VTL's steer(), which is why a VTL correction must be a small Kp-like number (about 0.3 to 0.45), not something like 300: that saturates both wheels every tick, and the narrow, fast Ranger spins off the line while the slower Scout can limp along.

7Maze solving and the motion layer

Maps are grids with per-cell wall flags (N/E/S/W), 180 mm cells and 12 mm walls (Micromouse proportions). Goals are a 1x1 or 2x2 region. Failure is a wall collision or exceeding 120 s of sim time.

  • Wall follower is cheap but fails on loops. The mz-island map exists on purpose to show that; flood fill solves it.
  • Flood fill runs in phases: explore to the goal while learning walls, compute shortest path, run it. It uses a distance field over discovered cells.
  • A motion layer turns discrete intents ("move to adjacent cell", "turn") into continuous wheel commands. Algorithms reason in cells; the layer owns the physics of getting there. This is also what lets VTL maze programs be short and safe.
Design lesson from bugs: early maze runs circled forever because the arrival target was recomputed from the robot's live position every tick, so the goalpost moved with the robot. Targets must be latched when a move is issued, not derived each tick.

8Rendering: 3D and 2D

  • R3F scene built from primitives with a directional light and shadows. Camera presets: isometric, top-down, chase (the chase camera rotates to the robot's heading rather than just translating).
  • 2D Canvas view is the debug layer and shares the same state.
  • Telemetry panel shows speed, wheel commands, error, P/I/D terms and an error-vs-time sparkline.
  • Pages are lazy-loaded so visiting the homepage never initializes Three.js or the sim engine.

9State management

One Zustand store holds mode, map, robot, algorithm, sensor layout, params, playback and telemetry. Every selection action goes through a single internal rebuild() that constructs a fresh engine snapshot and updates state atomically, then calls persist().

Why one rebuild path: it makes "selection changed" the only way an engine gets created, so there is no half-updated state where, say, the robot changed but the sensors still belong to the old chassis.

A real bug in this area

Custom sensor layouts are fit to a specific chassis, so switching robots deliberately does not carry the old robot's layout over. The original implementation reset to the new robot's built-in default every time, which meant saving a custom layout for one robot, switching away and switching back lost it. Fix: a layoutByRobot map remembers each robot's own last layout. It is an additive field in the save, so old saves backfill to {} with no version bump. Chassis-scoping is preserved: you only ever get that robot's layout back.

10Persistence and migrations

  • Save lives under vectortrack.v3: last session, tuned params, best runs, completed maps, settings, per-robot layout memory. Custom maps and custom algorithms have their own keys so a bad write to one never corrupts another.
  • Never lose user data: v1 → v2 was purely additive; v2 → v3 rewrote best-run keys to include the sensor layout id (a best time under one sensor layout is not comparable to another). Migration reads the old key, writes the new one, and falls back to defaults on any parse error.
  • Additive fields over version bumps: new fields are simply absent in old saves and the {...defaults, ...parsed} spread backfills them.
  • Debounced writes (500 ms) because param sliders fire constantly, plus flushSaveData() on pagehide/beforeunload. Without the flush, saving a sensor layout and reloading inside the debounce window silently reverted to Default. Reproduced and fixed with a test.
  • Storage failures (quota, disabled) are swallowed: persistence must never crash the app.

11Routing and deployment

  • HashRouter, not BrowserRouter: GitHub Pages is a static host with no rewrite rules, so a deep link like /simulator would 404 on refresh. Hash routes sidestep that with zero server config.
  • Vite base: '/VectorTrack/' for the project-page subpath. A case mismatch in that base once produced a blank deployed site, a good example of something that works in dev and breaks in prod.
  • Deployment: GitHub Actions on push to main: npm ci → npm run test:run → npm run build → upload to Pages. Tests gate the deploy.
  • Static pages in public/ (such as this one) are copied verbatim into the build and are outside the SPA router, so they are reachable by URL without being linked from the app.

12The map maker

  • Maze editor: a lattice canvas where you toggle wall segments, place start and goal.
  • Line editor: a paint grid. Rule: store the paint grid, never the bitmap. The smooth track is recomputed from the grid (maps/line/smoothing.ts), so saves stay tiny and the renderer can improve without migrating data.
  • Pan and zoom live in a pure canvasView.ts (zoom toward cursor, clamped 1 to 8x), so the math is unit-testable without a DOM.
  • Validation: started with many rules and blocked Save; after user feedback I cut the heuristics nobody could act on rather than just downgrading them. Remaining rules measure something actionable (corridor width vs chassis, turn clearance, sensor range). Lesson: a warning the user cannot act on is noise.
  • An AI map generation skill file is downloadable, so an LLM can emit maps in the editor's format.

13VTL: the custom algorithm language

Why a language instead of a JS sandbox

  • Running user JS safely in a browser (eval, workers, timeouts) is hard to make airtight and impossible to make deterministic.
  • A small language gives static guarantees: bounded cost, no recursion, no randomness, errors with line and column.
  • Compile errors name the mode ("can_move is a maze builtin") instead of failing at runtime.

Pipeline

source text -> lexer -> parser (AST) -> analyzer (scopes, types, mode rules, loop bounds)
            -> interpreter (tree-walk, per-tick node budget)

Source text is the stored form, never a compiled artifact: the AST is re-derivable in microseconds.

Language shape

  • Python-like indentation blocks (LLMs write them reliably), param / state / let / set, on tick: events, one grammar for both modes with different builtins in scope.
  • for i in a..b: with mandatory bounds: a literal, len(x) or sensor_count(). No while, no recursion, no user functions.
  • state x[N] = v arrays and flat row-major table literals (a square table renders as a grid in the editor); steer(base, correction) and deriv(e, tau) as sugar over the PID math.

Safety model (two layers)

  1. Compile time: loop bounds must be statically known, so cost can be checked before running. A bad bound is a line-numbered error (VTL015), and a statically known budget overflow is VTL014.
  2. Runtime: a hard per-tick evaluated-node budget (16384, nesting depth 3). This is what actually makes it hang-proof and would catch any construct the static check missed. Computed array indices are checked at runtime (VTL017).
Key insight: the runtime budget, not the absence of while, provides safety. Bounded loops are required so the cost can be rejected early with a good message, and because they push maze algorithms into the right shape.

Errors are part of the product

Every message names the problem, line and column, and what is available. This matters doubly because the language is designed to be written by LLMs too: a downloadable skill file documents the grammar, and good errors let a model self-correct.

Hot-swap

Editing code mid-run recompiles and keeps matching state (scalars and arrays) by name and type, resetting anything whose type or length changed. Tested for both scalar and array cases.

Equivalence testing

The VTL PID rewritten with steer/deriv is tested to match the explicit hand-written PID tick for tick, and VTL wall follower/flood fill are checked against the native TS versions. That is what justifies calling the shorthand "sugar".

14Sensor layout editor

  • Drag sensors on a chassis outline; 1 mm grid snap, Shift for free placement; undo/redo; presets; named saved layouts; JSON import and export.
  • Layouts are mode-typed (reflectance for line, rangefinder for maze) and tied to a chassis via basedOnRobotId. The sim and the sidebar both resolve the active layout through the same resolveLineSensorPlacements/resolveMazeSensorPlacements functions, falling back to the robot's default if a layout is missing or the wrong type, so a deleted layout can never crash a run.
  • Import is defensive: accepts a bare array or an envelope, fills missing optional fields, regenerates ids (never trust imported ids), rejects wrong-type sensors, and applies atomically so a bad file never half-replaces the canvas.
  • Best-run keys include the layout id, so times are only compared like for like.
Bug story: the sidebar displayed the robot's static sensor count even after a custom layout changed it, because it read the robot spec instead of the same resolver the sim uses. Rule of thumb: display code must read through the same resolution path as execution code.

15Testing and verification

  • Roughly 370 Vitest tests: kinematics, sensors, runners (full laps as integration tests), VTL lexer/parser/analyzer/interpreter, adapters, store, persistence migrations, equivalence and determinism tests.
  • Run it, don't just read it. Several serious bugs were invisible to unit tests and review but showed up the moment a real program ran end to end (see the lexer bug below). I made "run the actual program headlessly before shipping a template" a habit, plus headless-browser checks for UI behavior.
  • tsc -b, not bare tsc --noEmit: the root tsconfig only has project references, so the latter checks nothing while the real build still fails. I was unknowingly trusting a no-op check for several phases.
  • oxlint with zero warnings caught a real rules-of-hooks violation in the sensor editor before the app was ever run.
  • CI runs the full suite before every deploy.

17Trade-offs and what I'd change

  • Kinematic only. No slip, inertia or motor lag, so tuned gains will not transfer exactly to hardware. The trade was determinism, speed and simplicity. A next step would be a first-order motor lag model.
  • Global gain scale. One ERROR_GAIN_SCALE is a compromise across robots. Per-robot scales or auto-normalization by max speed and wheelbase would be more principled.
  • localStorage only. No sync or sharing beyond JSON export. Fine for a static site; a backend would be needed for leaderboards.
  • Tree-walking interpreter. Plenty fast at 120 Hz with a 16k-node budget; compiling to closures would only matter for much larger programs.
  • HashRouter URLs are less clean than path routes, in exchange for zero hosting config.
  • Tests pass but the environment couldn't always drive a real browser. I compensated with headless Playwright scripts, but a standing end-to-end suite would be better than ad hoc scripts.
  • Mobile is not optimized; desktop-first by scope.

18Likely interview questions

Why separate the simulation from the renderer?
Testability and swappability. The core is pure TypeScript, runs in Node, and feeds both a Canvas and a Three.js renderer from the same state. It let me assert on full laps in tests with no GPU, and it guarantees the 2D and 3D views cannot diverge.
How do you keep the simulation deterministic?
Fixed 1/120 s timestep with an accumulator (speed multiplier changes steps per frame, not dt), no random sources, strict source-order evaluation in VTL, and tests that run the same program twice and compare trajectories.
Why invent a language instead of letting users write JavaScript?
Safety and guarantees. A sandboxed JS runtime is hard to make airtight and cannot promise bounded cost or determinism. VTL has no unbounded loops or recursion, a per-tick node budget, mode-checked builtins, and line-accurate errors, and its compile-time loop-bound check turns would-be hangs into early, readable errors.
How does VTL prevent infinite loops?
Two layers: loops require literal, len() or sensor_count() bounds so cost can be checked before running, and a runtime evaluated-node budget per tick backs it up regardless.
How did you handle changing the save format without losing data?
Additive fields where possible (missing keys backfilled by spreading over defaults), and explicit versioned migrations when semantics change, like adding the layout id to best-run keys. Migrations read the old key, write the new one, and fall back to defaults on any failure; storage errors never crash the app.
Why HashRouter?
GitHub Pages cannot rewrite unknown paths to index.html, so path-based deep links 404 on refresh. Hash routes need no server configuration.
Tell me about a hard bug.
The multi-line table literal: a trailing ] was lexed through the 2-char operator branch because slice clips silently at end of line. It was a latent bug that only mattered once I added bracket-depth tracking to one branch. Unit tests of the grammar passed; running the real Sugeno program exposed it. The fix was a one-line length guard plus an end-to-end regression test.
How did you decide what to test?
Pure logic gets unit tests (kinematics, lexer, migrations); behavior gets integration tests (a robot completes a lap); anything a user could see differ gets an equivalence or end-to-end check. After finding that review alone misses bugs, I treated "ran it and observed it" as the bar for behavior claims, and walked the spec's acceptance criteria one by one, which found an implemented-but-untested array hot-swap path.
What would you do differently?
Add a persistent end-to-end browser suite rather than ad hoc scripts, introduce per-robot control scaling instead of one global constant, and add a motor lag model so tuned gains are more realistic.
How does the app scale if there were 100 maps or algorithms?
Pages are lazy-loaded, maps and algorithms are data with caps (50 custom algorithms/layouts) and quota-aware writes, and the sim only builds an engine for the current selection. The rendering and sim cost is per-run, not per-library-size.
